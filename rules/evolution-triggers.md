# rules/evolution-triggers.md — 自进化触发规则

> 触发：空闲/每日收尾/用户纠正。作用：把候选观察凝练成规则。

### 触发时机

| 场景 | 动作 |
|---|---|
| 任务收尾（无论成败） | 沉淀检查（O1）：有新失败/疑问/偏好 → 结构化写入 observations.md |
| 每日收尾 / 空闲 | bash scripts/evolution-cycle.sh（完整一轮） |
| 用户明确纠正/给偏好 | 立即 --record 记观察，标注 source=user |
| 同一失败模式出现 | 记录 observation + events.log |
| 仅想分析不动手 | bash scripts/evolution-cycle.sh --dry |
| 进展停滞（信号触发） | 同一任务/主题多轮无新结果 → 暂停执行，跑反思轮 |

> 信号触发：反思不只看固定时间（cron 每 4h），更看信号——每 5-10 次实验后、出现重复模式时、进展停滞时，都该主动反思一次。

### 纠错闭环（Codex 记忆规则补强）

- 信号记录与修正注入分离：失败/纠正发生时，当前步骤只记录信号（events.log + observations）；修正包在下一模型步骤前注入，不中途改变当前决策上下文
- Trace 采样：梦境循环读候选时，按 task/tool/error signature 同时取高价值 + 低价值样本
- LLM 只生成带 evidence 的候选，不直接覆盖 Active
- 灰度近似：晋升后进 --verify 观察期，连续回归切回 last-known-good（不死鸟 restore）

### 任务收尾沉淀检查（O1）

> 定时梦境会漏——会话结束那一刻是最佳捕获点。每次任务收尾（成败不论）过一遍四问，有新东西才写，不写流水账。

1. 失败/卡点：本次有失败、熔断、阻塞吗？→ 写 observation + events.log（带反思三字段）
2. 用户偏好/纠正：用户给了新偏好或纠正吗？→ 写 observation（source=user）
3. 重复模式：某种操作模式出现 ≥2 次了吗？→ 记候选，为技能生长（O2）攒证据
4. 结论/决策：本次达成了什么值得跨任务记住的？→ 写 observation 或当日笔记

钩子位置：任务完成汇报前 30 秒自查；长任务每完成一个里程碑也过一遍。

### 梦境循环流程（v3 结构化晋升）

1. 读 observations.md + 最近每日笔记
2. 按晋升门判断候选是否够格
3. 够格 → 归档候选到 evolution-log.md（不再叠加进 learned-rules.md）→ 人工重构：与现有 R1-R8 对比，合并去重后写入/更新规则（防叠加）
4. 不够格 → 保持候选层（不强行晋升）
5. 下轮巡检跑 evolution-cycle.sh --verify：检查已晋升规则的行为符合度
   - 符合 → 验证台账标 ✅ 并移除
   - 不符合 → 标 ❌ 并 phoenix-snapshot.sh restore 回滚
6. 上行同步 Obsidian（vault-sync.sh up）

v3 变化：v2 的"cat 观察 → 追加 learned-rules"导致 6 批叠加（7 个节头/编号重置）。v3 改为归档 + 人工重构。

核心原则：晋升不再是终点。规则必须被验证真的改变了行为；无效规则会被回滚。

防叠加铁律：同一主题只保留一条最优规则；新候选先与现有 R1-R8 对比，重复则合并不新增。

修复范围纪律：调试/修复时——①诊断信号先行 ②只修根因相关代码 ③回归用二分定位 ④视觉类回归用截图对照。

### 规则写入前提（TDD 适配）

没有失败测试不许写生产代码。沉淀新规则前，先回答：
1. 失败基线：没有这条规则时，行为会在什么场景失败？（写进观察记录）
2. 验证标准：有了这条规则后，怎么判断它生效了？
3. 回滚条件：什么信号说明这条规则有害？（台账标 ❌ → 不死鸟 restore）

失败测试必须来自独立真值源：
- ❌ tautological（恒真）→ 用已知字面量/手算示例/spec 作真值源
- ❌ implementation-coupled（测内部实现）→ 只测外部行为
- ❌ horizontal slicing（先写完全部测试）→ 垂直切片（一个测试→一个实现→重复）

### 晋升前对抗审查

非平凡决策交给对抗评审（偏向证伪）：
- "这条规则在什么情况下是错的？"
- "它会伤害什么本来正常的行为？"
- "它是否与已有 rules/ 或红线冲突？"

发现实质缺陷 → 打回候选层；无明显缺陷 → 才可晋升。

- 自动化（source=dreaming-narrative）→ 系统按晋升门判断
- 人工（source=user 明确纠正）→ 记录后仍需确认才进长期层（用户明确说"记住这个" = 直接晋升，带 scope=user 标记）

### 反馈闭环

corrections（用户纠正/失败）→ observations（候选）
→ learned-rules（多证据规则）→ rules/scripts（运行时约束）→ evolution-log

规则落成运行时约束后，这条经验才真正"进化"了——不是记下来了，是改行为。
