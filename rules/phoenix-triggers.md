# rules/phoenix-triggers.md — 不死鸟触发规则

> 触发：工具失败/状态异常。这是自愈行为契约，不是文档。

### 熔断（Circuit Breaker）

- 同一工具连续失败 3 次 → 熔断
  - 停止重试该工具
  - 记录 memory/events.log
  - 切换替代策略（换工具/换路径/换模型）
- 单点阻塞立即停止：执行中遇到阻塞（缺依赖/验证失败/指令不清/计划有致命缺口）→ 立即停止并求助，不硬闯。
- 反馈回路优先：修 bug 先构建可复现/可观察的反馈回路（完成标准 = 稳定触发失败），再动手修复。
- 双轴审查：审查任务先定固定点，沿 Standards + Spec 双轴并行审查，并排报告。
- 熔断期间安全工具（读记忆、写笔记、查会话、phoenix status）永远放行

### 失败记录格式（反思三字段，O3）

events.log 失败/纠正条目强制带三字段（可精简到一行）：
<时间> | fail | <事件> | 原因:<根因> | 尝试:<已试路径> | 下次:<策略/升级>

- 只记"失败"没写"下次"的条目 = 无效账本，梦境循环跳过它
- 同一失败模式累计 3 次 → 自动成为 observations.md 候选
- 静态追踪验证：自动化脚本/迁移类任务无法端到端运行时，静态追踪——枚举的每个值都落位，替代实跑。
- 防作弊验收：验收"测试绿"可能是 .skip/放松断言/mock/删测试——基线不可退、点名禁止姿势、暗卷自留；幻觉命令对策：每条命令亲手跑过；静默事故对策：亲手制造一次失败证明会响。
- 发布前预检：确认在正确分支/工作树再动手；发布走取 diff→范围审查→再 ship。
- 致命缺陷审计 + 诚信门：评估方案先找必死缺陷排除，再谈价值；收尾过诚信门（数据/引用/复现性核查，编造一票否决）。

### 交付复核标准（R10 补强）

> 触发：收到任何 agent（尤其 gm）的交付。原则：**不只听汇报，独立复核产出**。

- 验收动作：查文件 → 跑测试 → 看代码质量 → 对照任务书验收标准
- 执行 agent 交付链路：走 TDD 红绿重构流程（先写失败测试→实现→重构）
- 复核人独立验证，不采信单方汇报；复核对不上 → 退回重做并记录 events.log
- 防作弊验收：点名禁止 .skip/放松断言/mock/删测试；基线不可退

### 健康检查（运行时）

- 状态异常时 → bash scripts/phoenix-snapshot.sh status 对比基线
- 差异 = 关键文件被改 → 判断是预期改动还是异常

### 回滚（Restore）

- 触发条件：关键文件被破坏/错误覆盖；框架/规则被改坏；实验性改动失败
- 执行：bash scripts/phoenix-snapshot.sh restore（非清空式，保留记忆与日志）
- 回滚后：记录 events.log + 写 observation（教训候选）

### 升级（Escalation）

同一问题 3 次未解决 → 升级链：
1. 查修复导图/知识库找历史方案
2. 上层 Agent / 用户

升级时必须带上：问题描述 + 已尝试 N 次 + 每次结果（events.log 引用）。

### 工具白名单（故障时仍可用）

- read / write（记忆区）/ exec（只读）/ memory_search / phoenix-snapshot status
- 这些永不熔断 —— 自愈的前提是能读能写记忆
